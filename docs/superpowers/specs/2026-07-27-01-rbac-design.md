# Design — `01-rbac/` chapter

**Date:** 2026-07-27
**Status:** Approved (design phase)
**Chapter:** `01-rbac/` — access by ROLE, the first hands-on lab of the SafiBank Cloud learning repo

---

## 1. Purpose

`01-rbac/` is the first chapter with **runnable code**. The reader learns RBAC by
*using* it: permissions attach to roles, users get roles, users inherit their role's
permissions. Then the chapter delivers the pivotal "RBAC breaks" moment that motivates
the entire rest of the repo (ABAC, ReBAC, policy-as-code).

Because it is the first hands-on chapter, its conventions (Python + Casbin, guided-menu
CLI, `model.conf` + `policy.csv` as data, a dev-only test file) set the **pattern every
later lab follows** (`02-abac`, `03-rebac`, …).

**Done-criteria for the reader.** After this chapter they can:

- Explain RBAC in one sentence: permissions → roles → users.
- Run the lab and read a verdict for any (subject, action, resource) triple.
- Explain **role inheritance** (Leila the `branch_manager` can transfer because she
  inherits `teller`).
- Name the three limits that push you to ABAC/ReBAC: **roles multiply**, **no context**
  (time/amount), **no relationships** (ownership).

**Explicit non-goals (YAGNI).**

- No ABAC/ReBAC logic — no time, amount, ownership, or branch matching in the policy.
  Those are *shown to be impossible* here, then delivered in later chapters.
- No web server, API, or database — the lab is a single local CLI.
- No freeform natural-language input parsing — input is a guided menu.
- No per-tool comparison content — that lives in `05-tools/`.
- Pytest is **not** taught as the reader experience; the test file is a dev/CI artifact.

## 2. Decisions (locked)

| Decision | Choice |
|----------|--------|
| Language / engine | **Python 3.9+ with `casbin` (pycasbin)** |
| Reader experience | **Interactive guided-menu CLI** (pick from lists, by name or number) |
| Extra CLI modes | A **`demo`** entry (runs all canonical scenarios) + a **"hit the wall"** entry |
| The "RBAC breaks" moment | **Hands-on** — an interactive step that poses a rule RBAC can't express |
| RBAC model | Standard Casbin RBAC **with role inheritance** (`g` role-definition) |
| Verification | A dev-only **`test_policy.py`** asserting the canonical scenarios (not part of the reader narrative) |

**Running-example cast** (reused verbatim from the repo blueprint, do not rename):

- Tenants: **DinarBank**, **Banque de Carthage**.
- People: **Mr. Youssef** (`customer`), **Amine** (`teller`), **Leila** (`branch_manager`),
  **Sonia** (`auditor`), **Karim** (`admin`).
- Resources: `account`, `transaction`, `loan`.
- Canonical test question (carried from `00-foundations`): *"Can teller **Amine**
  transfer **8,000 TND** from **Mr. Youssef's account** at **22:00**?"* — in RBAC the
  answer ignores the amount and time (RBAC can't see them); that gap is the chapter's
  climax.

## 4. The RBAC model (`model.conf` + `policy.csv`)

### `model.conf` — standard Casbin RBAC with role inheritance

```ini
[request_definition]
r = sub, obj, act

[policy_definition]
p = sub, obj, act

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act
```

### `policy.csv` — everything as data, not code

```csv
p, customer,       account, view
p, teller,         account, view
p, teller,         account, transfer
p, branch_manager, loan,    approve_loan
p, auditor,        account, view

g, amine,   teller
g, leila,   branch_manager
g, youssef, customer
g, sonia,   auditor
g, branch_manager, teller
```

**Teaching beats this encodes:**

- Permissions attach to **roles**, never directly to people.
- `g, branch_manager, teller` gives Leila every teller permission **by inheritance** —
  the role hierarchy in one line.
- Access changes = editing a CSV, not editing code.
- `customer → view account` is deliberately **coarse** (role-level): pure RBAC cannot say
  "his *own* account." That coarseness is called out in the break, not hidden.

## 5. The interactive experience (`main.py`)

A guided menu. No freeform text parsing — the reader always picks from known lists (by
number or lowercase name), so no input can be "held wrong."

**Main loop:**

1. **Who's asking?** — `amine` (teller) · `leila` (branch_manager) · `youssef` (customer)
   · `sonia` (auditor).
2. **Do what?** — `view` · `transfer` · `approve_loan`.
3. **On which resource?** — `account` · `loan`.
4. Print the verdict + a one-line *why*, e.g.
   `✅ ALLOW — Amine is a teller; tellers may transfer on account.`
   `❌ DENY — Youssef is a customer; customers may not transfer.`

**Two special menu entries** (offered alongside the cast in the top-level menu):

- **`demo`** — evaluates all **9 canonical scenarios** and prints an ALLOW/DENY table
  (see §6). Shows inheritance and denials at a glance.
- **`wall`** ("Try a rule RBAC can't express") — poses *"a teller may transfer, but only
  during branch hours (08:00–17:00), only from his own branch, only his own account."*
  Prints an explanation (static, no evaluation needed): `policy.csv` has columns for
  **subject / object / action** and **no column for time, amount, or ownership**; faking
  it explodes roles (`teller_morning` → `teller_morning_tunis` →
  `teller_morning_tunis_under_10k` …). Ends by pointing to `02-abac`.

**Decision helper.** A single function `decide(enforcer, sub, obj, act) -> bool` wraps
`enforcer.enforce(...)`. Both the interactive loop and `demo` call it, and
`test_policy.py` imports it — one source of truth for "ask the PDP."

**Enforcer construction.** A `build_enforcer(model_path, policy_path) -> casbin.Enforcer`
factory builds from the two files, so tests can construct an enforcer without running the
menu. `model.conf` and `policy.csv` are resolved relative to `main.py`'s own directory
(works regardless of the caller's CWD).

## 6. Canonical scenarios (the `demo` table and the test oracle)

| # | Subject | Role | Action | Resource | Expected |
|---|---------|------|--------|----------|----------|
| 1 | Amine | teller | view | account | ✅ ALLOW |
| 2 | Amine | teller | transfer | account | ✅ ALLOW |
| 3 | Amine | teller | approve_loan | loan | ❌ DENY |
| 4 | Leila | branch_manager | approve_loan | loan | ✅ ALLOW |
| 5 | Leila | branch_manager | transfer | account | ✅ ALLOW (inherits teller) |
| 6 | Leila | branch_manager | view | account | ✅ ALLOW (inherits teller) |
| 7 | Youssef | customer | view | account | ✅ ALLOW |
| 8 | Youssef | customer | transfer | account | ❌ DENY |
| 9 | Sonia | auditor | transfer | account | ❌ DENY |

These nine are the single source of truth: `demo` prints them, `test_policy.py` asserts
them. Scenarios 4–6 prove role inheritance; 3, 8, 9 prove denial.

## 7. Testing / verification

**`test_policy.py`** (pytest) — dev/CI artifact, not shown as the reader's path:

- Builds an enforcer via `build_enforcer` from the real `model.conf` + `policy.csv`.
- One assertion per canonical scenario in §6 (9 checks), each calling `decide(...)`.
- Verifies role inheritance explicitly (Leila can `transfer`) and denial (Youssef cannot).

**Editorial verification** (docs):

- All internal links resolve (`theory.md`, `hands-on-casbin/README.md`, forward link to
  `02-abac/`).
- Cast names, roles, resources, and the canonical test question match the blueprint and
  `00-foundations` exactly (no drift).
- `hands-on-casbin/README.md` run steps actually work end-to-end (venv → install → run).
