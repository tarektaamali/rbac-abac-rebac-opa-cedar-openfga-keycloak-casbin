# Design — `02-abac/` chapter

**Date:** 2026-07-27
**Status:** Approved (design phase)
**Chapter:** `02-abac/` — access by ATTRIBUTES, the payoff chapter of the SafiBank Cloud learning repo

---

## 1. Purpose

`02-abac/` is where the repo's canonical question finally gets the **right** answer.
Chapter 1 (RBAC) said "Amine is a teller, tellers may transfer → allow," ignoring the hour
and amount. This chapter **layers attributes on top of that role**: the same teller, the
same transfer, now correctly **denied at 22:00** (after branch hours) and **denied over
10,000 TND** and **denied across branches**.

It reuses chapter 1's cast, tool (Python + Casbin), and three-mode CLI shape
(`ask` / `demo` / `wall`), so the reader feels the continuity: RBAC did not get thrown
away — ABAC *augmented* it.

**Done-criteria for the reader.** After this chapter they can:

- Explain ABAC in one sentence: decide using **attributes** of subject/resource/action/context,
  not just a role.
- Explain that **ABAC augments RBAC** (the role check stays; conditions are added).
- Run the lab and watch the **same** transfer flip ALLOW→DENY when only the **hour** changes.
- Name ABAC's new costs: harder "why was I denied?" debugging, and clumsiness with
  **ownership / relationships** (the bridge to ReBAC).

**Explicit non-goals (YAGNI).**

- No ReBAC (relationships, ownership graphs) — the `wall` step only *points* to `03-rebac`.
- Only the **teller transfer** rule gains attribute conditions; all other rules stay
  unconditional (`cond = true`). This keeps the diff from chapter 1 sharp and the lesson
  focused.
- No web server, API, database, or policy-as-code externalization (that's chapter 4).
- No freeform natural-language input — input stays a guided menu.
- Pytest remains a dev/CI artifact, never presented as the reader's path.

## 2. Decisions (locked)

| Decision | Choice |
|----------|--------|
| Framing | **ABAC layers on top of RBAC** — role check kept, conditions added |
| Where conditions live | **In `policy.csv` as a new condition column**, evaluated via Casbin `eval(p.cond)` — "rules stay data," same lesson as ch1 |
| Which rules get conditions | **Only `teller transfer`**; all others `cond = true` |
| Lab shape | **Mirror ch1's three modes**: `ask` / `demo` / `wall`, now context-aware |
| Demo headline | The **09:00 → ALLOW vs 22:00 → DENY** flip on the same transfer |
| `wall` points to | **`03-rebac`** (ownership / relationships ABAC handles clumsily) |
| Engine | Python 3.9+, `casbin` (pycasbin). Fallback if `eval()` misbehaves: a registered matcher function (documented in the plan) |

**Running-example cast** (reused verbatim from the blueprint and chapters 0–1; do not rename):

- People + home branch: **Amine** (`teller`, Tunis), **Leila** (`branch_manager`, Tunis),
  **Mr. Youssef** (`customer`, Tunis), **Sonia** (`auditor`, read-only / branch irrelevant).
- Resources: `account`, `loan`.
- Context attributes: `amount` (TND), `hour` (0–23), `sub_branch`, `obj_branch`.
- Canonical test question (answered correctly for the first time here): *"Can teller
  **Amine** transfer **8,000 TND** from **Mr. Youssef's account** at **22:00**?"* → **DENY**
  (after branch hours).

## 4. The model (`model.conf` + `policy.csv`)

### `model.conf` — RBAC role check plus an evaluated condition

```ini
[request_definition]
r = sub, obj, act, amount, hour, sub_branch, obj_branch

[policy_definition]
p = sub, obj, act, cond

[role_definition]
g = _, _

[policy_effect]
e = some(where (p.eft == allow))

[matchers]
m = g(r.sub, p.sub) && r.obj == p.obj && r.act == p.act && eval(p.cond)
```

### `policy.csv` — chapter 1's rules plus a condition column

```csv
p, customer, account, view, true
p, teller, account, view, true
p, teller, account, transfer, r.amount <= 10000 && r.hour >= 8 && r.hour < 17 && r.sub_branch == r.obj_branch
p, branch_manager, loan, approve_loan, true
p, auditor, account, view, true

g, amine, teller
g, leila, branch_manager
g, youssef, customer
g, sonia, auditor
g, branch_manager, teller
```

**Teaching beats:**

- The **only** new thing versus chapter 1 is the condition column, and the **only**
  non-trivial condition is on `teller transfer`. The `git diff` against ch1's `policy.csv`
  literally *is* "ABAC = RBAC + conditions."
- Conditions live in **data** (the CSV), not code — same "access is data" lesson as ch1.
- Branch hours are `08:00–17:00` → `r.hour >= 8 && r.hour < 17`. The limit is `10,000 TND`
  inclusive → `r.amount <= 10000`. Same branch → `r.sub_branch == r.obj_branch`.

## 5. Attributes, the request, and `decide()`

- Each person has a **home branch** (`sub_branch`), from a table in `main.py`:
  Amine/Leila/Youssef → `Tunis`, Sonia → not branch-scoped.
- The account's branch is `obj_branch`, chosen at ask-time (or fixed per demo scenario).
- The Casbin request is fixed-arity, so **every** `enforce` call passes all seven fields.
  For rules whose `cond` is `true`, the context values are ignored but still supplied.

**Decision helper** (single source of truth, used by CLI, demo, and tests):

```
decide(enforcer, sub, obj, act, *, amount=0, hour=12, sub_branch="", obj_branch="") -> bool
```

- Keyword-only context with neutral defaults, so `view` / `approve_loan` calls stay simple
  (`decide(e, "youssef", "account", "view")`).
- Internally calls `enforcer.enforce(sub, obj, act, amount, hour, sub_branch, obj_branch)`
  and coerces to `bool`.

**Enforcer factory:** `build_enforcer(model_path=None, policy_path=None) -> casbin.Enforcer`,
paths defaulting to the files next to `main.py` (CWD-independent), identical pattern to ch1.

## 6. The three modes (`main.py`)

- **ask** — guided menu: subject → action → resource. **Only for `transfer`**, then prompt
  guided **amount** [`5000` / `8000` / `12000`], **hour** [`9` / `22`], **account branch**
  [`Tunis` / `Sfax`]. `sub_branch` is taken from the chosen person. Print verdict + one-line
  why (e.g. `❌ DENY — after branch hours (22:00 is outside 08:00–17:00).`).
- **demo** — `run_demo(enforcer) -> list[tuple]` returns labeled rows for these canonical
  scenarios; `main` prints them as a table:

  | Subject | Action | Amount | Branch | Hour | Expected | Reason |
  |---------|--------|--------|--------|------|----------|--------|
  | Amine | transfer | 8000 | Tunis | 09:00 | ✅ ALLOW | within hours, under limit, same branch |
  | Amine | transfer | 8000 | Tunis | 22:00 | ❌ DENY | after hours |
  | Amine | transfer | 12000 | Tunis | 09:00 | ❌ DENY | over 10,000 |
  | Amine | transfer | 8000 | Sfax | 09:00 | ❌ DENY | wrong branch (Amine is Tunis) |
  | Leila | transfer | 8000 | Tunis | 09:00 | ✅ ALLOW | manager inherits teller |
  | Youssef | transfer | 8000 | Tunis | 09:00 | ❌ DENY | customer role can't transfer |

- **wall** — static text pointing to `03-rebac`: a rule ABAC handles clumsily — *"only the
  account's **owner** may close it"* and *"the manager of the **branch that owns** it"* —
  where faking ownership needs ever-more synced attributes, and **relationships** are the
  clean answer. Ends pointing at chapter 3.

## 7. Testing / verification

**`test_policy.py`** (pytest, dev/CI only):

- Builds an enforcer via `build_enforcer` from the real `model.conf` + `policy.csv`.
- Asserts the canonical flip: Amine transfer 8000/Tunis/**09:00** → True; same at **22:00** → False.
- Asserts over-limit (12000 → False) and wrong-branch (obj_branch Sfax → False).
- Asserts role inheritance still holds under ABAC: Leila transfer 8000/Tunis/09:00 → True.
- Asserts unconditional rules ignore context: Youssef `view account` → True with no context;
  Sonia `transfer` → False.
- Asserts `run_demo` returns the 6 rows above with expected verdicts.
- Asserts `build_enforcer` is CWD-independent.

**Editorial verification** (docs): internal links resolve; cast/wording/canonical question
match chapters 0–1; `hands-on-casbin/README.md` run steps work end-to-end; the `policy.csv`
diff from ch1 is exactly "add a condition column + one real condition."
